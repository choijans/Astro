# Astro Channel Management Portal: Product Requirements Document

Status: Draft v1 (pre-build) · 24 Oct 2026

## 1. Purpose

Build a portal to browse Astro channels, view channel details, manage favourites and process queued user commands. This is the Astro Full Stack Engineering Technical Assessment (estimated effort 3-5 days). This PRD fixes scope, behaviour and decisions before coding, and becomes the source for the README.

## 2. Goals and non-goals

**Goals**

- Deliver every mandatory requirement from the brief: listing with search and sorting, details page, responsive UI, state management, Channels and Favourites APIs, database integration, unit tests, README and architecture diagram.
- Deliver the queue challenge: ADD_FAVORITE, REMOVE_FAVORITE and REFRESH_CHANNEL, multiple users, 5-second outage recovery.
- Make the project runnable by a reviewer from a fresh clone with Docker only.
- Show clean layering (SOLID), validation and tests.

**Non-goals**

- User registration, login or real authentication.
- Manual creation, editing or deletion of channels (channels come from sync).
- Video playback or streaming.
- Copying Astro's UI, styling or branding.
- AWS or live hosting (only if time remains).

## 3. Assumptions

- Channel data comes from Astro's content API list endpoint, found through browser dev tools on the Astro content portal (URL: https://contenthub-api.eco.astro.com.my/api/v2/search-linear?channelGuide=true&platform=acm&channelOrderBy=stbNumber,asc). It is undocumented and may change, so it sits behind an adapter and a committed snapshot.
- Response shape: the channels are wrapped in an envelope, so the adapter reads `response.channels.data` and checks `responseCode`. The query string is required to get this shape and is hardcoded in the client. The response also holds a `linearContent` collection, which is ignored. All channels arrive in one response, so there is no upstream paging.
- Fields used: id, title, subtitle, imageUrl, detailUrl, stbNumber, category, genreKey[], languageKey[], rangeKey, ranking, currentSchedule[]. stbNumber arrives as a string and is stored as an integer. Some channels carry extra flags (isAstroFirstExclusive, isAstroGoExclusive, isRadioExclusive); these are dropped on ingest.
- Data quirks: the subtitle is usually "CH 100" but not always, so it is displayed as given. Ranking has ties, which is why every sort ends with the channel ID. Titles can repeat across channels. Astro gives no last-updated time, so "last updated" is our own sync time.
- Identity is an anonymous user ID generated by the frontend, stored in localStorage and sent as an `X-User-Id` header. No auth.
- Reviewers have Docker installed. Postgres and Redis run in containers; the apps run with `npm run dev`.

## 4. Functional requirements

| ID | Requirement | Acceptance criteria |
|---|---|---|
| FR-1 | Channel listing | Cards show logo, title, the subtitle exactly as supplied (usually "CH 100", but some channels use other text, so no prefix is assumed) and category. Infinite scroll: the first 24 channels load, and the next page loads automatically as the user nears the bottom. Pages use a stable order (sort field, then ID) so no channel repeats or is skipped. The list is served from the database, never by calling Astro at request time. |
| FR-2 | Search | Case-insensitive match on channel title or channel number (typing 100 finds CH 100). Debounced input. Clear empty state when nothing matches. |
| FR-3 | Sorting | Sort by channel number (default, ascending), title, or ranking, ascending or descending. Channel number sorts numerically. |
| FR-4 | Filtering | Filter by category, language and genre, plus channel number range (0-199, 200-299, and so on up to 800-899, from Astro's rangeKey), which is built after the core filters. Filters combine with each other, with search and with sort. State lives in URL query params so a view can be shared and survives reload. |
| FR-5 | Channel details | Route `/channels/:id` shows logo, title, number, category, languages, genres, current schedule (title, start and end in MYT), last-updated time (our own sync time, since Astro supplies none), a favourite button and a Refresh button that queues REFRESH_CHANNEL for that channel. Astro's own page URLs appear only as a View on Astro link. Unknown ID shows a not-found page. |
| FR-6 | Favourites | Toggle from card and details page. A Favourites view shows only saved channels. UI updates optimistically and rolls back if the command fails. Favourites persist across reloads. |
| FR-7 | Commands | ADD_FAVORITE, REMOVE_FAVORITE and REFRESH_CHANNEL are submitted to the API, queued, processed asynchronously and their status can be read. |
| FR-8 | Data sync | A seed script loads the committed snapshot. Refresh pulls fresh data from Astro. Sync is an idempotent upsert and tolerates Astro being down. |
| FR-9 | Responsive UI | Usable from 360px phones to desktop. Filters collapse into a drawer on small screens. |
| FR-10 | UI states | Every data view has loading, error (with retry) and empty states. |

## 5. Non-functional requirements

- **Performance:** database indexes on title, channel number and category. Redis caching: list responses expire after 30-60 seconds (they vary by search, sort and filter, so they are not invalidated key by key); a channel's detail cache is cleared when that channel is refreshed.
- **Security:** DTO validation with whitelisting on every input, helmet, CORS restricted to the frontend origin, rate limiting on write endpoints, no secrets in the repo (`.env.example` only).
- **Reliability:** commands are persisted before they are queued, retried with backoff and idempotent.
- **Maintainability:** controller, service, repository layering. One handler class per command type. TypeScript strict mode, lint and format config.
- **Scalability and extensibility:** stateless API, the worker is a separate process from the same codebase and can run as several instances, a new command type means a new handler class and nothing else.
- **Observability:** structured logs and a `/health` endpoint that checks the database and Redis.
- **Accessibility:** semantic HTML, keyboard-operable controls, labelled inputs.

## 6. System architecture

```
Next.js frontend (Zustand, TanStack Query, offline outbox)
        |  REST / JSON
NestJS API (Channels, Favourites, Commands modules)
   |            |              |
Postgres     Redis        AstroClient --> Astro content API
(Prisma)  (cache + BullMQ)
                 |
          NestJS worker (command handlers) --> Postgres
```

**Read flow:** frontend calls `GET /channels`, API checks Redis, falls back to Postgres, returns a page of results.

**Favourite flow:** user taps the heart, UI updates optimistically, frontend sends the command with a client-generated UUID, API validates and saves it as PENDING, adds it to the queue and returns 202. The worker applies it and marks it DONE. The frontend reconciles on the next read.

**Refresh flow:** a REFRESH_CHANNEL command names one channel. The worker fetches Astro's channel list (reusing a copy cached for about a minute), updates that channel's data and schedule, and invalidates its Redis cache entries. Several refreshes of the same channel at once collapse into one job.

## 7. Data model

| Table | Columns |
|---|---|
| channels | id (Astro ID, primary key), title, subtitle, stb_number (integer), image_url, category, genres (text[]), languages (text[]), range_key, ranking, schedule (jsonb), schedule_updated_at, created_at, updated_at |
| favourites | user_id, channel_id, created_at. Unique on (user_id, channel_id). |
| commands | id (UUID from client), seq (server-assigned order), user_id, channel_id, type, payload (jsonb), status, attempts, error, created_at, processed_at |

Indexes: channels(title), channels(stb_number), channels(category), favourites(user_id), commands(user_id, channel_id, type, seq).

## 8. API specification

| Method and path | Purpose | Success | Errors |
|---|---|---|---|
| GET /channels | List with q, sort, order, category, language, genre, range, page, limit | 200 | 400 invalid params |
| GET /channels/filters | Distinct categories, languages, genres and number ranges | 200 | none expected |
| GET /channels/:id | Channel details with schedule | 200 | 404 |
| GET /favourites | Current user's favourites | 200 | 400 missing user header |
| POST /favourites | Wrapper that enqueues ADD_FAVORITE | 202 | 400, 404 unknown channel |
| DELETE /favourites/:channelId | Wrapper that enqueues REMOVE_FAVORITE | 202 | 400 |
| POST /commands | Generic command entry (all three types) | 202 | 400, 429 |
| GET /commands/:id | Command status | 200 | 404 |
| GET /health | Liveness and dependency check | 200 | 503 |

All errors use one shape: `statusCode`, `message`, `error`. All writes go through the queue, so there is one write path: the favourites routes and POST /commands call the same CommandsService.enqueue function. Rate limiting applies to POST /commands, POST /favourites and DELETE /favourites/:channelId.

## 9. Queue and outage design

**Lifecycle:** PENDING, PROCESSING, DONE or FAILED.

**Rules (proposed):**

1. Persist the command in Postgres before enqueueing. The database is the source of truth.
2. The client-generated UUID is the idempotency key. Re-sending the same ID never creates a second command.
3. Handlers are idempotent: adding an existing favourite or removing a missing one counts as success.
4. Ordering per user: the server gives every command a sequence number, and the worker skips a command if a newer one for the same user and channel was already applied, so add-then-remove cannot flip. This ordering applies to ADD_FAVORITE and REMOVE_FAVORITE only. REFRESH_CHANNEL is separate: it collapses per channel across all users, and every user's command is still marked DONE.
5. Retries: exponential backoff, enough attempts to span well over 5 seconds.
6. Recovery sweep: on API or worker start, when Redis reconnects, and on a 5-10 second timer as a backstop, re-enqueue commands still PENDING in the database. The command UUID is the queue job ID, so re-enqueueing a command that is already queued cannot create a duplicate. This covers Redis being down at enqueue time.
7. Frontend outbox: if the API is unreachable, commands wait in localStorage and are resent with the same IDs when the connection returns.

**Interpretation of "5-second outage recovery":** if the API, worker or Redis is unavailable for about 5 seconds, no command is lost and every command is applied exactly once after recovery.

**Acceptance test:** submit a batch of commands from two users while stopping Redis (or the worker) for 5 seconds, restore it, then confirm all commands end DONE with no duplicate favourites and correct final state per user.

## 10. Testing strategy

| Layer | Tool | Focus |
|---|---|---|
| Backend units | Jest with mocked repositories | Command handlers (idempotency, duplicates), channel query service (search, sort, filter), AstroClient tested against a saved real response (envelope unwrapping, stbNumber cast, flags dropped, failure handling) |
| Backend API | Jest and Supertest | Validation errors, happy paths, 202 responses, 404s, status endpoint |
| Frontend components | Jest and React Testing Library | Search, sort and filter behaviour, favourite toggle including rollback, loading, error and empty states |
| Outage scenario | Scripted test or documented manual run | The 5-second recovery acceptance test above |

Tests run locally with `npm test` in each app. CI (if time allows) runs the same commands.

## 13. Risks

| Risk | Mitigation |
|---|---|
| Astro API changes, blocks or goes down | Adapter interface, committed snapshot, graceful failure in sync |
| Detail page URL contains a build ID that changes | Do not depend on it. Build details from stored list data |
| Five unfamiliar tools at once (Jest, Supertest, RTL, Zustand, TanStack Query) | Learn each when first needed, start with one test per layer |
| Scope too large for 3-5 days | Follow the cut line above |
| Reviewer cannot run the project | Docker Compose, `.env.example`, tested README steps, fresh-clone check |
| Port 5432 already used on the dev machine | Document the 5433 mapping |
